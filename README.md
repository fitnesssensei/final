# Keitaro wrapper — тестовое задание ETOLEGKO

Обёртка над [Keitaro](https://keitaro.io) Admin API: создание кампаний с гео-потоком
и редактор офферов с «верными цифрами» из отчётов трекера.

- Backend: FastAPI + SQLAlchemy 2.0 (async) + Alembic + Pydantic v2 + httpx
- Frontend: серверный HTML (Jinja2) без сборки и JS-фреймворков
- Хранение: источник истины — Keitaro, локальная БД хранит журнал операций,
  кэш справочников и настройки

## Архитектура

```
браузер (HTML-формы)              curl / скрипты (JSON)
        │                                  │
        ▼                                  ▼
api/routes/ui.py  ──── общий роутер ────  api/routes/campaigns.py
        │                                  │
        └────────────────┬─────────────────┘
                         ▼
                     services/            создаватель, редактор,
                         │                справочники, идемпотентность
              ┌──────────┴──────────┐
              ▼                     ▼
        keitaro/                db/ (SQLAlchemy async)
   client, DTO, ошибки      operation_log + dictionary_cache
              │
              ▼
       Keitaro Admin API   (источник истины)
```

- `api/` — только HTTP: разбирает ввод, вызывает сценарий и переводит доменные
  ошибки в коды (JSON) или в страницу с текстом (UI), успех UI — редирект 303.
- `services/` — сценарии: создание кампании с двумя потоками и компенсацией,
  правка офферов с пересчётом весов, цифры из отчёта, обновление кэша
  справочников, идемпотентность через `operation_log`.
- `keitaro/` — единственное место с httpx: заголовок `Api-Key`, таймауты,
  ретраи и маппинг ответов и ошибок в доменные исключения.
- `db/` — журнал операций (ключ, тело, статус, снимок ответа) и кэш
  справочников; кампании и офферы живут только в Keitaro.

## Требования

- Python 3.12–3.13 (на 3.14 нет wheels `asyncpg`) и [uv](https://docs.astral.sh/uv/)
- Docker и Docker Compose — для запуска с PostgreSQL

Зависимости зафиксированы в `uv.lock`: в `pyproject.toml` только нижние границы,
а `uv sync` (он же `make install`) ставит проверенные версии из lock-файла —
установка воспроизводима, без «внезапных» мажорных обновлений.

## Запуск локально

```bash
cp .env.example .env      # и заполнить: ключ и адрес Keitaro
make install              # uv sync
docker compose up -d db   # PostgreSQL для миграций и журнала операций
make migrate              # alembic upgrade head
make run                  # http://127.0.0.1:8000
```

`make run` без Postgres тоже работает для `/health`, но ручки, которые пишут
журнал операций (шаги 4–5), без миграций вернут 503 с подсказкой
«выполните make migrate» — сначала `make migrate`.

Проверка:

```bash
curl -s localhost:8000/health
# {"status":"ok","version":"0.1.0"}

open http://127.0.0.1:8000/docs
open http://127.0.0.1:8000/ui/creator   # создаватель
open http://127.0.0.1:8000/ui/editor    # редактор
```

`/health` — только живость процесса: настройки он не читает и зависимостей не
трогает. Обязательные переменные проверяются на старте (`lifespan`), поэтому с
пустым ключом или `http://` в адресе сервис не поднимется и напишет, какие поля
не прошли валидацию. В Docker это видно как упавший контейнер `app`, а не
«зелёный» healthcheck.

`/ready` — готовность: делает `SELECT 1` в локальной БД. Пока Postgres выключен
или миграции не накатаны, ручка отвечает `503`:

```bash
curl -s -i localhost:8000/ready
# 200 {"status":"ready","version":"0.1.0","database":"ok"}
# 503 {"status":"not_ready","database":"unavailable","detail":"база не отвечает: ..."}
```

Разделение важное: liveness не должен перезапускать процесс из-за выключенной
БД (`/health` остаётся `200`, чтение Keitaro работает), а readiness честно
сообщает «журнал операций писать некуда». Keitaro эти пробы не дёргают — его
отказ виден на конкретной ручке (`502`).

## Запуск в Docker

```bash
docker compose build app
docker compose up -d db
docker compose run --rm app alembic upgrade head   # миграции до старта приложения
make up        # app + PostgreSQL (порт хоста 5433, чтобы не мешать локальному Postgres)
make logs
make down
```

Контейнер `app` запускается с двумя воркерами uvicorn (`--workers 2`) и
перезапускается при падении (`restart: unless-stopped`). В образе `HEALTHCHECK`
дёргает `GET /health` (живость), а `docker-compose.yml` переопределяет пробу на
`GET /ready`: контейнер считается здоровым только когда отвечает БД. Пока
миграции не накатаны, `docker compose ps` покажет `unhealthy` — это подсказка
выполнить `docker compose run --rm app alembic upgrade head`. С неверным `.env`
контейнер падает на старте и уходит в перезапуск — причина видна в
`docker compose logs app`.

## Тесты и линтер

```bash
make test      # uv run pytest -q (253 теста)
make lint      # uv run ruff check .
make format    # uv run ruff format .
```

Те же проверки идут в GitHub Actions (`.github/workflows/ci.yml`) на каждый push
в `main` и на pull request: `ruff check`, `ruff format --check`, `pytest -q`,
затем `alembic upgrade head` → `alembic check` → `downgrade base` →
`upgrade head` на настоящем Postgres 17 (сервис-контейнер). Keitaro в CI не
нужен: все тесты герметичные, ответы трекера — двойник и `respx`.

Тесты не ходят в сеть: ответы Keitaro замоканы `respx`, а БД — файл SQLite во
временном каталоге `tmp_path` (Postgres для тестов не нужен). Настройки
поднимаются в изолированном окружении (`tests/conftest.py` гасит `KEITARO_*`
и сбрасывает кэш). Отдельный тест прогоняет `alembic upgrade head` → `downgrade
base` на SQLite и сверяет таблицы и колонки с моделями, чтобы миграция не
разошлась со схемой. Ручки создания и редактора проверяются с двойником
Keitaro (`tests/stub_keitaro.py`): сверяются точная форма payload'ов обоих
потоков, компенсация, веса 50/50 и 34/33/33, цифры из мока отчёта, повтор с
тем же ключом и коды ошибок. UI проверяется теми же `httpx`-запросами:
рендер страниц, селекты из кэша, создание через форму, добавление/удаление
оффера, ошибки 4xx/5xx и экранирование HTML.

## Конфигурация

Все значения читаются из окружения и `.env` (в git не попадает; шаблон —
`.env.example`).

| Переменная | Обязательная | Назначение |
|---|---|---|
| `KEITARO_BASE_URL` | да | адрес инстанса, например `https://example.keitaro.io` |
| `KEITARO_API_KEY` | да | Admin API key, передаётся заголовком `Api-Key` |
| `KEITARO_DOMAIN_ID` | да | домен кампании по умолчанию |
| `KEITARO_GROUP_ID` | да | группа кампаний по умолчанию |
| `KEITARO_SOURCE_ID` | да | источник трафика по умолчанию |
| `KEITARO_GOOGLE_URL` | нет | редирект гео-потока, по умолчанию `https://www.google.com` |
| `KEITARO_TIMEOUT` | нет | таймаут одного запроса в секундах, по умолчанию `60` (на живом инстансе `POST /streams` не укладывался в 10 с, и создание падало в 502) |
| `KEITARO_RETRIES` | нет | число повторов сверх первой попытки, по умолчанию `1` (допустимо 0–5) |
| `DATABASE_URL` | нет | строка подключения SQLAlchemy, по умолчанию локальный Postgres на 5433 |
| `LOG_LEVEL` | нет | `critical`…`debug`, по умолчанию `info`; применяется к логированию приложения |
| `AUTH_USER` | нет | логин HTTP Basic для `/api/*` и `/ui/*`; пусто/не задано — без авторизации |
| `AUTH_PASSWORD` | нет | пароль HTTP Basic; задаётся только вместе с `AUTH_USER` (половина пары — ошибка старта) |
| `REFERENCE_CACHE_TTL` | нет | сколько секунд справочники считаются свежими, по умолчанию `900`; `0` — обновлять только пустой кэш |
| `OPERATIONS_RETENTION_DAYS` | нет | сколько дней хранить журнал операций, по умолчанию `7`; `0` — хранить бессрочно |

Отсутствие обязательной переменной, пустой ключ или `http://` в адресе инстанса —
понятная ошибка на старте (с перечнем полей), а не падение в рантайме на середине
запроса и не `401` от Keitaro.

Авторизация необязательная: без пары `AUTH_USER`/`AUTH_PASSWORD` сервис открыт,
как локальный инструмент. Если пара задана, `/api/*` и `/ui/*` требуют HTTP
Basic (`curl -u user:password …`, браузер показывает окно входа), а `/health` и
`/ready` остаются открытыми — их дёргают Docker и оркестратор без учётных данных.
Пустые `AUTH_USER=`/`AUTH_PASSWORD=` считаются выключенной авторизацией, а
заданная половина пары — ошибка старта: «почти включённая» защита опаснее
отсутствующей.

Справочники в селектах обновляются сами, когда истёк `REFERENCE_CACHE_TTL`
(по умолчанию 15 минут), и по кнопке «обновить» (`?refresh=1`). Журнал операций
чистится на старте: записи старше `OPERATIONS_RETENTION_DAYS` удаляются
(подробности — в логе); при недоступной БД старт не падает, чистка просто
пропускается. Ключи идемпотентности удаляются вместе с записями, поэтому
срок хранения выбирайте не меньше того, на который может растянуться повтор
запроса клиентом.

## Создание кампании

`POST /api/campaigns` создаёт кампанию и два потока по контракту из
`docs/campaign-create.md`:

1. поток `regular/redirect` с единственным фильтром `country = <geo>` (accept)
   редиректит на Google (`KEITARO_GOOGLE_URL`);
2. поток `default/landings` без фильтров отдаёт трафик на оффер со `share=100`.
   Если Keitaro уже создал `default`-поток сам, он обновляется через `PUT`,
   чтобы не появилось два дефолтных.

Домен, группа и источник по умолчанию берутся из `KEITARO_*` и проверяются по
кэшу справочников (при промахе кэш обновляется из Keitaro). Те же значения можно
передать в запросе полями `domain_id`, `group_id`, `traffic_source_id` —
так делает UI, когда пользователь выбирает их в селектах. Оффер читается
напрямую: он должен существовать и быть `active`.

```bash
curl -s localhost:8000/api/campaigns \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-1' \
  -d '{"name": "MX test", "geo": "MX", "offer_id": 18813}'
```

```json
{
  "campaign_id": 215000,
  "alias": "mx-test-a1b2c3",
  "name": "MX test",
  "geo": "MX",
  "offer_id": 18813,
  "streams": [
    {"id": 1, "name": "Google (MX)", "type": "regular", "schema": "redirect", "position": 1},
    {"id": 2, "name": "Offers", "type": "default", "schema": "landings", "position": 2}
  ],
  "idempotency_key": "demo-1",
  "replayed": false
}
```

Поля запроса: `name` (1–255), `geo` (ISO-2, приводится к верхнему регистру),
`offer_id` (положительный), необязательные `domain_id`/`group_id`/
`traffic_source_id`. Ответ — `201`; повтор с тем же `Idempotency-Key`
возвращает сохранённый результат с `replayed: true` и кодом `200`, не создавая
вторую кампанию. Без заголовка сервер генерирует ключ и возвращает его в теле
и в заголовке `Idempotency-Key`.

Компенсация: если после создания кампании упал поток, кампания архивируется
(`DELETE /campaigns/{id}`), в журнал пишется ошибка; если архив не удался, в
тексте ошибки есть подсказка удалить кампанию вручную. Если кампания и потоки
уже созданы, а упала запись журнала, кампания **не** удаляется — в журнале и
логе остаётся просьба проверить её в Keitaro.

| Код | Когда |
|---|---|
| 201 / 200 | кампания создана / повтор с тем же ключом |
| 409 | ключ уже использован с другим телом, операция ещё выполняется или прошлая попытка упала |
| 422 | гео не ISO-2, оффер не найден/неактивен, домен/группа/источник из `.env` отсутствует в Keitaro, Keitaro отклонил payload |
| 502 | Keitaro недоступен, отклонил ключ или вернул неожиданный ответ (подробности в логе) |
| 503 | не накатаны миграции или недоступна БД |

## Редактор кампании

| Ручка | Назначение |
|---|---|
| `GET /api/campaigns` | список кампаний (заодно обновляет кэш для селектов) |
| `GET /api/offers` | список офферов (кэш для селекта «добавить оффер») |
| `GET /api/campaigns/{id}?interval=all_time` | потоки, офферы, веса и цифры |
| `POST /api/campaigns/{id}/offers` | добавить оффер в поток `{"offer_id": 18813, "stream_id": 1335650}` (`stream_id` необязателен) |
| `DELETE /api/campaigns/{id}/offers/{offer_id}?stream_id=…` | удалить оффер из потока (`stream_id` необязателен) |

Правила весов: после добавления/удаления доли офферов пересчитываются поровну
и всегда дают в сумме 100% — два оффера 50/50, три 34/33/33. Позиции — порядок
в потоке, 1..N. Последний оффер удалить нельзя: поток остался бы без трафика
(422).

Поток для добавления адресуется явно: `stream_id` в теле `POST .../offers` и
селект в форме редактора. Селект показывает только потоки, куда оффер вообще
можно поставить (схема не `redirect`), и предвыбирает непустой поток —
непустой `default`, иначе единственный поток с офферами. Если потоки
неоднозначны (офферы лежат в нескольких), предвыбора нет: в селекте пустой
пункт «— выберите поток —», и без явного выбора форма не отправится. Без
`stream_id` (совместимость с прежним API) работает то же правило выбора:
непустой `default` → единственный поток с офферами → пустой `default`; если
потоков с офферами несколько — 422 «выберите поток». Удаление в UI тоже
отправляет `stream_id` (форма), а `DELETE ...?stream_id=…` адресует поток так
же явно, как `POST`: без параметра работает то же правило выбора, с параметром
удаляется оффер именно из этого потока (несуществующий `stream_id` или оффер не
в этом потоке → 404, `stream_id=0` → 422).

Если один и тот же оффер стоит в нескольких потоках, у каждой пары
(поток, оффер) свой `Idempotency-Key`: удаление из первого потока больше
не «засчитывается» как действие во втором, а повтор с тем же ключом и другим
`stream_id` даёт 409.

Одновременные правки одного потока не сериализуются: Keitaro не отдаёт версию
потока (ETag/updated_at), а `PUT /streams/{id}` принимает поток целиком. Если
два человека (или две вкладки) с разными ключами прочитают поток и оба сохранят
свою версию, второй `PUT` перезапишет офферы первого. Для локального
инструмента это осознанное ограничение: действия идут по одной форме за раз,
а повтор по тому же `Idempotency-Key` безопасен.

Поток отправляется в `PUT` целиком (`StreamUpdate`): `triggers`, `landings`,
`weight`, `state`, `comments`, фильтры сохраняются, даже если редактор меняет
только `offers`. Живой Keitaro отдаёт `action_options` как `null`, объект или
список, а `country.payload` — списком или строкой (`"RU AU"`); обе формы
поддерживаются и возвращаются без изменений.

Цифры — из `POST /report/build`: отчёт запрашивается с
`dimensions=["campaign_id","stream_id","offer_id"]` и фильтром
`campaign_id EQUALS <id>` (`FilterRequest` из спецификации), а строки
дополнительно сверяются по id. Все три измерения проверены на живом инстансе
21.11.2026: строки приходят по потокам, `offer_id = 0` — клики не на оффер
(редиректы). Поэтому цифры привязаны к паре (поток, оффер): одинаковые имена
офферов не складываются, а один оффер в двух потоках показывает свои числа в
каждом. Итог кампании — сумма всех строк, включая редиректы.
`interval` — диапазон Keitaro (`all_time`, `today`,
`7_days_ago`, `1_month_ago`, …), по умолчанию `all_time`. Если отчёт упал, не
уложился в таймаут или вернул строки без `campaign_id`, кампания всё равно
возвращается: `stats_available=false` и баннер «цифры недоступны» — нули вместо
неизвестных значений не показываются. Причина остаётся в логе. Таймаут
поднимается через `KEITARO_TIMEOUT` (по умолчанию 60 с): на живом инстансе
`POST /streams` и отчёт иногда отвечают дольше 10 секунд.

```bash
curl -s localhost:8000/api/campaigns/215000
curl -s -X POST localhost:8000/api/campaigns/215000/offers \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: add-1' \
  -d '{"offer_id": 18813, "stream_id": 1335650}'
curl -s -X DELETE localhost:8000/api/campaigns/215000/offers/18813 \
  -H 'Idempotency-Key: remove-1'
```

Мутации идемпотентны по `Idempotency-Key` (как создание): повтор возвращает
сохранённый результат с `replayed: true` и кодом 200, не трогая Keitaro.
В UI ключ генерируется на каждое действие формы.

## Интерфейс (Jinja2, без сборки)

| Страница | Что делает |
|---|---|
| `/ui/creator` | форма создания: название, гео, оффер, домен, группа, источник |
| `/ui/editor` | селектор кампании и периода, потоки, офферы, веса и цифры |
| `/` | редирект на создаватель |

Страницы серверные: формы отправляются обычным POST, ошибки возвращаются той же
страницей с текстом (422/409/404/502/503), успех — redirect 303. JavaScript
используется только для подтверждения удаления. Селекты берутся из
`dictionary_cache`; при первом открытии пустые справочники читаются из Keitaro
один раз. В редакторе есть кнопка «Обновить кэш» (`?refresh=1`), она
перечитывает кампании и офферы.

Создаватель передаёт выбранные `domain_id`, `group_id`, `traffic_source_id` в
`POST /api/campaigns` (поля необязательные: без них берутся `KEITARO_*` из
`.env`). Редактор меняет офферы через те же сервисы, что и API; скрытые
`Idempotency-Key` в формах защищают от двойного клика и сетевого ретрая.

### Ручной чек-лист UI

- [ ] `/ui/creator` открывается, в селектах есть домен/группа/источник и офферы;
      при первом заходе справочники подтянулись из Keitaro.
- [ ] Создать кампанию на тестовом стенде: 303 → редактор, кампания и два потока
      видны, в уведомлении «Кампания создана».
- [ ] Добавить второй оффер: доли 50/50, `Σ 100%`, цифры по офферам видны.
- [ ] В форме добавления проверить селект потока: на кампании с пустым `default`
      и оффером в другом потоке предвыбран поток с оффером; если офферы лежат в
      нескольких потоках — пустой пункт «— выберите поток —» и без выбора форма
      не отправляется.
- [ ] Удалить второй оффер: остаётся 100%, уведомление «Оффер удалён».
- [ ] Попробовать удалить последний оффер: 422 с объяснением, поток не тронут.
- [ ] Добавить уже стоящий оффер: 409 «уже есть».
- [ ] Двойная отправка формы добавления (или повтор с тем же скрытым ключом):
      второй запрос не меняет Keitaro, доли те же.
- [ ] При недоступном отчёте страница открывается, показывает предупреждение
      «Цифры временно недоступны», офферы редактируются.
- [ ] Пустой список кампаний: пустое состояние со ссылкой в создаватель.
- [ ] Переключить период цифр и кампанию — селектор сохраняет выбор.
- [ ] Проверить в браузере, что `<script>` в названии кампании экранируется.
- [ ] Оффер стоит в двух потоках: у кнопок «Удалить» разные ключи, удаление из
      второго потока не трогает первый.

Живые записи в общий тестовый стенд выполняйте осознанно: кампании создаются
настоящие, удаление оффера меняет поток в Keitaro.

## Как использовались ИИ-агенты

По ТЗ это приветствуется, поэтому коротко и без прикрас:

- Работа шла по плану `План_ETOLEGKO_Keitaro.md`: один шаг — одна порция
  изменений, после каждого шага прогон `pytest`/`ruff` и короткий отчёт.
- Агент (Cline в режимах plan/act) писал код, тесты и документацию. Разведка
  Admin API на живом инстансе, решения по бизнес-логике, коммиты и запуск
  `docker compose` оставались за человеком.
- На баг сначала писался воспроизводящий тест (он падал), потом фикс: так
  закрыты 500 на `offer_id <= 0` и общий ключ удаления для одного оффера в
  двух потоках (подробности — в `review.md`).
- Код-ревью в `review.md` тоже делал агент: найденные дефекты он подтверждал
  временными тестами, а сами тесты после проверки удалял, чтобы не оставлять
  мусор в наборе.
  
## Структура

```
src/keitaro_wrapper/
  main.py           сборка FastAPI-приложения, старт и валидация настроек
  config.py         настройки (pydantic-settings)
  logging_setup.py  применение LOG_LEVEL
  api/router.py     корневой роутер
  api/routes/       JSON-ручки и HTML-страницы (ui.py)
  services/         бизнес-сценарии: создаватель, редактор, справочники
  keitaro/          клиент Admin API, DTO и доменные ошибки
  db/               модели, сессии, журнал операций, кэш справочников
  templates/        Jinja2-шаблоны создавателя и редактора
migrations/         env.py и версии миграций Alembic
tests/              pytest
```

`services/` знает про Keitaro и БД, но не про HTTP: ручка только вызывает
сценарий и переводит доменные ошибки в коды ответа.

## Миграции

```bash
make migrate        # uv run alembic upgrade head
make migrate-down   # откат последней миграции
```

Три ревизии: `0e1c7bf97570` (локальные таблицы), `8b1e4c7d2a90` (снимок
результата операции), `c4f7a1d2b3e5` (удаление неиспользуемой `geo_map` от
первой версии кэша гео).

URL берётся из `DATABASE_URL`/`.env`, дефолт — Postgres из compose. Ключи
Keitaro для миграций не нужны: `migrations/env.py` не требует `KEITARO_API_KEY`.
В Docker миграции запускаются отдельной командой (файлы `alembic.ini` и
`migrations/` включены в образ):

```bash
docker compose run --rm app alembic upgrade head
```

Приложение не мигрирует БД само и не проверяет соединение на старте: движок
ленивый, поэтому `/health` и чтение Keitaro работают и без Postgres. Если схема
не накатана или БД недоступна, ручки с журналом отвечают **503** с текстом
«Локальная база не готова: выполните `make migrate` …» (`OperationalError`,
`ProgrammingError`, `ConnectionError` и таймаут пула перехватываются в
`api/errors.py`), а подробности попадают в лог приложения.
